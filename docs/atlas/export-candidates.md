# Trust Relay → Atlas — Export Candidates

This page is the **mirror image** of [Atlas — Import Candidates](./import-candidates): instead of asking *what should Workflow adopt from Atlas*, it asks **what could Atlas adopt from TrustRelay Workflow**. It is an exhaustive, honest catalog of every Workflow feature, each judged on whether it fills a genuine Atlas gap — verified against the actual Atlas codebase, not assumed.

The assessment produced **182 feature assessments** across 12 domains (a handful of cross-cutting capabilities — e.g. sanctions FP suppression, the financial-distress models, the EVOI budget engine — are assessed under more than one domain lens, so the distinct-feature count is somewhat lower). Each was checked against the Atlas repository and given a verdict:

- 🟢 **Strong** (40) — fills a real Atlas gap with high compliance or commercial value.
- 🟡 **Moderate** (70) — useful, but lower priority or partial overlap with something Atlas already has.
- ⚪ **Marginal** (43) — niche or nice-to-have.
- 🔴 **Redundant** (29) — Atlas already has an equivalent or better.

## The one question that decides almost everything

Most of these verdicts are **conditional on a single strategic choice**: *what is Atlas for?*

- **Atlas as an investigation microservice** (the path recommended in the codebase comparison — Atlas runs the parallel OSINT engine, Workflow owns case management, the portal, documents, and regulatory reporting). Under this model, most of Workflow's customer-facing, document, PII, and reporting features are **not** things Atlas should absorb — they belong in the Workflow layer that wraps Atlas. Importing them would duplicate the platform boundary.
- **Atlas as a standalone end-to-end compliance product** (Atlas sold on its own, competing with Workflow rather than composing with it). Under this model the same features become **essential** — Atlas cannot onboard a real KYB customer without a portal, document validation, PII protection, and SAR generation.

Atlas's own code shows it is **already drifting toward the standalone model**: it has built a workflow-engine *portal phase* (it pauses and waits for `submit_form_data`) and server-side document validation — but it has no public route, no portal UI, and no customer token model to actually serve them. It built the back half of an onboarding flow and not the front half. That tension is the single most important context for the verdicts below: **the 🟢 Strong customer-facing and document items are only strong if Atlas commits to the standalone path** — but the evidence suggests it is heading there.

A second, **strategy-independent** category exists: deterministic, self-contained analytics that improve *any* compliance product regardless of architecture — the sanctions false-positive suppression engine, the financial-distress models, PII encryption, and shell-company detection. These are pure-Python, byte-replayable, and drop into Atlas's `asyncpg` stack with near-zero framework friction (no PydanticAI→LangGraph rewrite). They are the safest, highest-ROI exports no matter which path Atlas takes.

## Strategic takeaway

Three clusters emerge from the 40 strong exports:

1. **Strategy-independent analytics (import regardless of path).** The sanctions false-positive suppression engine, the Altman/Ohlson/Zmijewski financial-distress models, column-level PII encryption + GDPR DSR, and shell-company / pure-mailbox detection are deterministic, self-contained, and pure-Python. They make any compliance product better, port with near-zero framework friction, and several (sanctions FP suppression, PII encryption) are direct commercial differentiators. **These are the first things to move.**

2. **The standalone-product front-half (import only if Atlas goes standalone).** The customer portal UI + capability-token model, white-label branding, OSINT-first dynamic document requirements, the document gap analyzer, automation tiers, goAML/SAR export, and the CopilotKit officer assistant are the missing front-half of an end-to-end onboarding product. Atlas has already half-built the portal phase, so the intent seems present — but each of these is wasted effort if Atlas stays the investigation engine behind Workflow.

3. **The authoritative-data moat (an architectural fork, not a simple import).** Workflow's country-routed registry agents (KBO, NBB, INPI, CZ ARES/CNB, KVK, ANAF…), PEPPOL verification, and the Lex regulatory corpus are its deepest data-quality advantage — but they are a deliberate departure from Atlas's web-search / MCP / provider-plugin strategy and carry L–XL porting cost. Adopting them means Atlas choosing authoritative-source depth over generic-coverage breadth.

**What Atlas should *not* import:** its risk engine already supersedes Workflow's (configurable matrix, factor-level overrides, batch/portfolio re-evaluation, schema lifecycle, Neo4j risk propagation), so the EBA-matrix and risk-config features are redundant; its entity reconciliation, event sourcing, ontology-schema versioning, Langfuse cost tracking, circuit breakers, and graph parity checking are equal or ahead. The one risk-adjacent gap worth importing is the **EVOI budget engine** — cost-governed adaptive investigation depth — which directly targets Atlas's LLM spend at portfolio scale.
